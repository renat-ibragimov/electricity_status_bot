# electricity_status_bot

Три независимых docker-compose проекта, которые вместе мониторят свет и
воздушную тревогу и пишут об этом в Telegram-каналы (Приморський и
Хаджибейський районні суди Одеси). Писалось давно, этот документ — карта, чтобы
не разбираться заново.

> Секреты (`.env`, токены, пароли БД, Telethon-сессия) в репе **не хранятся**.
> Ниже только имена переменных.

## Состав

| Папка | Что делает | Контейнеры |
|---|---|---|
| `api_db/` | FastAPI-приёмник «пингов» + Postgres | `api_db-api-1` (порт 8008→8000), `api_db-postgres-1` (порт 5435→5432) |
| `primorskii_court_bot/` | Бот «свет есть / света нет» | `primorskii_court_bot-bot-1` |
| `alert_status/` | Бот воздушной тревоги | `alert_status-alert_status-1` |

Все три используют **один Postgres** из `api_db` (проброшен наружу, остальные
ходят к нему по `DB_HOST:DB_LOCAL_PORT`).

### Свет (`api_db` + `primorskii_court_bot`)
1. У кого-то дома устройство/скрипт раз в минуту дёргает `GET :8008/<user_id>`.
   API пишет время в таблицу `times`.
2. `primorskii_court_bot/bot/start_bot.py` раз в 59 с смотрит последний пинг
   `USER_ID`: свежее 60 с → «⚪️ Світло є», старше → «⚫️ Світла немає».
   Смена статуса пишется в `statuses` и уходит в канал (`BOT_TOKEN`, `CHANNEL_ID`).

### Тревога (`alert_status`) — актуальное
Бот читает Telegram-канал-источник **через Telethon** (пользовательская
сессия `electricity_status_bot.session`, `TG_API_ID`/`TG_API_HASH`) раз в 60 с
и при смене статуса шлёт сообщение в каналы через Bot API
(`PRIMORSKII_COURT_BOT_TOKEN` → `PRIMORSKII_COURT_CHANNEL_ID` и
`HADJIBEYSKII_COURT_CHANNEL_ID`, см. `tg_bot.py`). Последний статус хранится в
таблице `alert_status` (создаётся вручную, в коде нет).

Файлы:
- `alert_checker.py` — главный цикл, источники, режимы миграции, тексты.
- `alert_parser.py` — чистый парсинг текста сообщений (без зависимостей).
- `test_alert_parser.py` — тесты парсера (`python3 -m pytest -q alert_status/test_alert_parser.py`).
- `db_worker.py`, `tg_bot.py`, `config.py` — БД, отправка, env.

#### Статусы и тексты уведомлений
`yellow`, `red`, `off`, плюс `on` (общая тревога без уровня: старый источник
или нераспознанный уровень). Уведомление уходит только при **смене** статуса
(сравнивается с последней строкой в `alert_status`, старые значения
`тревога!`/`тревоги` нормализуются в `on`/`off`).

- 🟡 `Повітряна тривога, жовтий рівень: <угроза>`
- 🔴 `Повітряна тривога, червоний рівень: <угроза>`
- 🟢 `Відбій повітряної тривоги`
- 🔴 `Повітряна тривога!` — `on` (старый формат)
- к каждому добавляется время Europe/Kyiv на второй строке.

#### Источники и миграция
| | Канал | Формат |
|---|---|---|
| старый | `SOURCE_CHANNEL_NAME` = `alertOdessa` | статус = последнее слово сообщения (`ALERT_ON`/`ALERT_OFF`), без уровней |
| **новый (сейчас)** | `NEW_SOURCE_CHANNEL_NAME` = `odesacityofficial` («Одеса. Офіційно») | `Одеський район — повітряна тривога, жовтий рівень: Дронова загроза (жовтий рівень)` / `… червоний рівень: Ракетна загроза …` / `Одеський район — відбій повітряної тривоги` |

Переключатель `ALERT_SOURCE_MODE` в `alert_status/.env`:
`legacy` (только старый) · `shadow` (старый шлёт, новый только пишет в лог
`[shadow] … would send`) · `new` (только новый).

**Текущее состояние (2026-10-01): на сервере `ALERT_SOURCE_MODE=new`.**
Переключено с `shadow` без длительного наблюдения: реального срабатывания
нового источника на живой тревоге ещё не видели — при первой тревоге проверить
лог и канал (см. «Проверка»).

#### Правила парсера нового канала (`parse_new`)
Канал также постит новости, поэтому сообщение считается оповещением, только
если оно **короткое (≤300 символов)** и **начинается с `NEW_SOURCE_AREA`**
(по умолчанию `Одеський район`; перед ним допускаются эмодзи). Внутри — по
корням слов, чтобы лучше отправить общую тревогу, чем пропустить:
`відбій` → off; нет `тривог` → не оповещение; `червон` → red; `жовт` → yellow;
иначе → on. Угроза — текст после `:` до `(`, необязательна. Нюанс: между
«район» и «—» стоит неразрывный пробел U+00A0. Проверено на ~120 реальных
сообщениях канала (85 оповещений, 38 новостей — ложных срабатываний нет).

Опрос: последние 5 сообщений, обрабатываются только новые id; при старте —
только актуальное последнее оповещение (история не переотправляется).
Ошибки чтения/отправки логируются, процесс не падает.

## Сервер и деплой

- DigitalOcean, `ubuntu-s-1vcpu-1gb-intel-fra1-01`, пользователь `renat`,
  ssh по ключу (IP — это `DB_HOST` в `.env`). **1 ГБ RAM, без swap.**
- Код лежит в `~/electricity_status_bot/{alert_status,api_db,primorskii_court_bot}`
  **без `.git`** — это копии. Серверные файлы правились руками и **расходились с
  репой** (на 2026-10-01 синхронизировано для `alert_status`). Перед деплоем
  всегда стягивать серверные версии и делать diff.
- Каждая папка — отдельный compose-проект; код смонтирован томом
  (`.:/<папка>/`), поэтому для правки `.py` пересборка не нужна — достаточно
  скопировать файлы и перезапустить сервис.
- На сервере крутятся **посторонние сервисы** (`r2u_bot`, `r2u_redis`,
  `mtproto-proxy` на 443 и мёртвые контейнеры `vinishko*` и др.). Не трогать.
  Перезапускать только нужный сервис: `docker compose restart alert_status`
  из его папки, никаких `docker restart`/`compose down` по маске.

### Выкатка `alert_status` (как делали)
1. Снимок `docker ps`, бэкап файлов и `.env` в `~/backups/alert_status-<ts>/`
   (последний — `~/backups/alert_status.latest`).
2. Проверить, что серверные `.py` не изменились (md5 против стянутых).
3. `scp` изменённых файлов; env править точечно (`sed -i` одной строки).
4. `docker exec alert_status-alert_status-1 sh -c 'cd /alert_status && python -m py_compile *.py'`.
5. `docker compose restart alert_status`, смотреть `docker logs`.

### Откат
В `alert_status/.env` поставить `ALERT_SOURCE_MODE=legacy`
(или `shadow`) и `docker compose restart alert_status`. Старые файлы — в
`~/backups/alert_status-<ts>/` (там же `.env.before-new`).

### Проверка
```
ssh renat@<host> 'docker logs --since 1h alert_status-alert_status-1 2>&1 | grep -v "wrong session ID" | tail -30'
ssh renat@<host> 'docker exec api_db-postgres-1 sh -c "psql -U \$POSTGRES_USER -d \$POSTGRES_DB -c \"select * from alert_status order by pk desc limit 5\""'
```
Ожидаемо при новой тревоге: в БД появляется `yellow`/`red`, в каналы приходит
сообщение с уровнем; при отбое — `off`. Ленту источника удобно смотреть в
Telegram Web (через Claude in Chrome), оттуда можно снять реальные тексты.

## Известные проблемы / долги
- **`wrong session ID` (Telethon)**: раньше логи были забиты этой ошибкой
  (десятки тысяч строк) и контейнер падал (24 рестарта). После переписывания
  и рестартов 2026-10-01 ошибка не повторялась, но причина не выяснена —
  подозрение, что тот же `.session` использовался где-то ещё (локально?).
  Не запускать Telethon с этой сессией параллельно с ботом.
- Логи контейнера раньше раздувались и чистились `truncate` руками —
  стоит добавить `logging: options: max-size` в `docker-compose.yml`.
- SQL в `primorskii_court_bot/bot/db_worker.py` и `get_status` собирается
  f-строками; у `api_db` нет авторизации (любой может слать пинги);
  Postgres проброшен наружу; в uvicorn стоит `reload=True`.
- `status_checker` при ровно 60 с между пингами ничего не делает.
- Таблица `alert_status` создаётся вручную; DDL в репе нет.
- Новый источник проверен только на ~6 днях истории: красных тревог 3,
  других типов угроз не видели.
